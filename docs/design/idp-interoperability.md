# Identity provider interoperability

The suite authorizes by governance functions (`contract/governance/README.md`). An identity
provider only has to put the organization's roles or groups in a claim; the governance model maps
them to functions, and every app (AOS, Prudence, Ernest) resolves the same token the same way. So
validating a provider means: its tokens are accepted (issuer, audience, signature), and the model
turns them into exactly the functions each person or workload should hold.

## The acceptance check

`scripts/idp-acceptance.sh` takes five tokens from the provider (an approver, an auditor, a
declarer, a decisions workload and an executions workload) and checks against a running Prudence:

- no token, a tampered signature and a token for another audience are refused (401);
- each person resolves to exactly their functions (`/api/me`);
- an auditor cannot approve, an approver cannot register, a person cannot call the PDP;
- the decisions workload reaches the PDP and an unregistered system is a `DENY`;
- the executions workload reaches `/api/executions` but not the PDP.

To see what any token gives in each app, without trusting the signature, use
`contract/governance/ct-model/ct_model.py explain MODEL TOKEN`.

Not covered yet: JWKS rotation, token expiry and role removal mid-session, duplicate emails across
issuers, and an outage of the provider itself.

## Dex

Dex suits reproducible local tests, not production.

- **Claims.** Dex puts a user's groups (static passwords or a connector) and a workload's
  `clientCredentialsClaims.groups` in `groups`, so the model needs
  `identity: {people: {claim: groups}, machines: {claim: groups}}`. It rejects custom scopes, so
  the default model's `scope` claim for workloads does not work with Dex.
- **Audience.** Tokens are issued for the requesting client. Add the API as a static client whose
  `trustedPeers` lists the consoles and workloads, and request
  `audience:server:client_id:prudence-api`; Dex then adds `prudence-api` to `aud`.
- **Login by email.** The local password connector signs in with the email, not the username.
- **Limits.** No `end_session_endpoint` (sign-out ends the console session only) and no
  `prompt=none` (no silent check across consoles).

## Microsoft Entra ID

Entra issues app roles in the `roles` claim, for users and for applications alike. That is what
the templates expect (`identity: {people: {claim: roles}, machines: {claim: roles}}`), and it
avoids group overage: app roles are emitted in full even when assigned through groups, where a
`groups` claim would be cut off at 200 groups.

### 1. One app registration for the suite

Create an app registration, for example **Chestertown**, in a development tenant:

1. **Expose an API.** Set the Application ID URI (`api://<client-id>`) and add a delegated scope
   `access_as_user`.
2. **Manifest.** Set `"requestedAccessTokenVersion": 2`, so the issuer is
   `https://login.microsoftonline.com/<tenant-id>/v2.0` and `aud` is the client id.
3. **App roles.** Generate them from the organization's model and paste the `appRoles` array into
   the manifest:

   ```bash
   contract/governance/ct-model/ct_model.py entra governance-model.yaml -o app-roles.json
   ```

   Person roles are for users and groups; machine roles (`runtime-decide`, `runtime-report`) are
   for applications only, so no person can hold `runtime.decide`.
4. **Authentication.** Add the platform *Single-page application* with the consoles' redirect URIs
   (Prudence `http://localhost:5200/`, AOS `http://localhost:5173/`, Ernest
   `http://localhost:5186/auth/callback`, or their deployed URLs). For the acceptance check only,
   enable *Allow public client flows* so people can get a token with the device code flow.
5. **Users.** In *Enterprise applications → Chestertown → Users and groups*, assign each test
   person one role (assigning to groups needs Entra ID P1 or higher).

Using one registration for the API and the consoles keeps the roles in both the access token
(AOS, Prudence) and the ID token (Ernest's console sends the ID token).

### 2. One app registration per workload

For the AOS runtime, create **chestertown-runtime-decide** (and **chestertown-runtime-report** if
another component reports executions). In *API permissions → APIs my organization uses →
Chestertown → Application permissions*, add the machine role and grant admin consent. Prefer a
certificate or a federated credential to a client secret.

### 3. Configure the apps

| App | Settings |
| --- | --- |
| Prudence | `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_ISSUER_URI=https://login.microsoftonline.com/<tenant-id>/v2.0`, `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_AUDIENCES=<client-id>`, `PRUDENCE_GOVERNANCE_MODEL=…`; console `VITE_OIDC_ISSUER` (same issuer), `VITE_OIDC_CLIENT_ID=<client-id>`, `VITE_OIDC_SCOPE="openid profile email api://<client-id>/access_as_user"` |
| AOS | `AOS_JWT_ISSUER` (same issuer), `AOS_JWT_AUDIENCE=<client-id>`, `AOS_JWK_URL=https://login.microsoftonline.com/<tenant-id>/discovery/v2.0/keys`, `AOS_GOVERNANCE_MODEL=…`; PDP client `PRUDENCE_PDP_TOKEN_URL=https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token`, `PRUDENCE_PDP_CLIENT_ID`/`PRUDENCE_PDP_CLIENT_SECRET` of the runtime registration, `PRUDENCE_PDP_SCOPE=api://<client-id>/.default`; console `VITE_OIDC_*` as for Prudence |
| Ernest | `OIDC_ISSUER` (same issuer), `OIDC_AUDIENCE=<client-id>`, `ERNEST_GOVERNANCE_MODEL=…`; console `PUBLIC_OIDC_ISSUER`, `PUBLIC_OIDC_CLIENT_ID=<client-id>`, `PUBLIC_OIDC_SCOPE` as above |

`ct_model.py env governance-model.yaml` prints the model settings.

### 4. Get the tokens and run the check

People, with the device code flow (each person signs in in the browser):

```bash
curl -s https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/devicecode \
  -d client_id=<client-id> -d "scope=api://<client-id>/access_as_user openid"
# open the URL it prints, enter the code, sign in as the test person, then:
curl -s https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token \
  -d grant_type=urn:ietf:params:oauth:grant-type:device_code -d client_id=<client-id> \
  -d device_code=<device_code>
```

Workloads, with the runtime registration's credential:

```bash
curl -s https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token \
  -d grant_type=client_credentials -d client_id=<runtime-client-id> \
  -d client_secret=<secret> -d "scope=api://<client-id>/.default"
```

Check each token with `ct_model.py explain`, then run `scripts/idp-acceptance.sh` with
`TOKEN_APPROVER`, `TOKEN_AUDITOR`, `TOKEN_DECLARER`, `TOKEN_DECIDE`, `TOKEN_REPORT` and, for the
audience check, `TOKEN_OTHER_AUDIENCE` (for example a Microsoft Graph token from the same tenant).
Record the result in the status table above.

## Identity settings that still apply

`PRUDENCE_IDENTITY_PRINCIPAL_MODE=issuer-subject` opts into stable issuer/subject identities; the
default `legacy` must remain until stored approvals and OPA grants are migrated.
`PRUDENCE_IDENTITY_POLICY_ACTOR_MODE` (default: the principal mode) switches only the policy
control plane to `<issuer length>:<issuer><subject>` actors, which managed mode requires.
`PRUDENCE_IDENTITY_ROLES_CLAIM` and `PRUDENCE_IDENTITY_ROLE_MAPPING` no longer authorize any
route (the governance model does); they still fill the `roles` that `/api/me` reports and the
roles a managed OPA policy evaluates. Production requires
`SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_AUDIENCES` (or `OIDC_AUDIENCES` with this repository's
Compose file), and both user and workload access tokens must carry an accepted audience.
